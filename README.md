# 1. Spirebound

## 텍스트 설계서에서 시작해 AI Coding Agent와 반복 개발한 웹 액션 로그라이크

🔗 [GitHub Repository](https://github.com/baggam-dev/spirebound)  
🔗 [Build Journal](https://github.com/baggam-dev/spirebound/blob/main/docs/build-journal.md)

### Why

생성형 AI를 이용해 단순한 코드 조각이 아니라, **지속적으로 수정하고 확장할 수 있는 하나의 애플리케이션을 어디까지 만들 수 있는지** 직접 실험해보고 싶었습니다.

먼저 게임 컨셉, 핵심 규칙, 진행 구조를 텍스트 기반 설계서로 작성했습니다. 전체 방향과 기능 우선순위는 제가 결정하고, 구현은 기능 단위로 나누어 AI Coding Agent에게 요청했습니다.

### Development Loop

    컨셉 / 설계
        ↓
    AI 구현
        ↓
    직접 플레이
        ↓
    플레이 후기 작성
        ↓
    문제 원인과 대안 상호 검토
        ↓
    수정
        ↓
    다시 플레이

한 번에 완성된 결과물을 요청하기보다, 직접 플레이하면서 발견한 문제를 다음 개발 요구사항으로 바꾸는 방식을 반복했습니다.

예를 들어 특정 공격 패턴이 지나치게 강하거나 특정 성장 방식의 효율이 과도한 경우 단순히 수치만 바꾸지 않고, 전투 패턴·성장 구조·반격 기회 등 여러 대안을 검토한 뒤 다음 구현 방향을 결정했습니다.

### My Role / AI Role

| 제가 담당한 부분 | AI Coding Agent에 맡긴 부분 |
| --- | --- |
| 게임 컨셉과 방향 정의 | 기능 단위 코드 구현 |
| 텍스트 기반 설계 및 요구사항 작성 | 기존 코드 분석 |
| 기능 우선순위 결정 | 수정안 및 구현 대안 제안 |
| 직접 플레이 테스트 | 회귀 테스트 작성 |
| 문제 발견과 요구사항 재정의 | 반복적인 수정·리팩터링 |
| 최종 적용 여부 판단 | 자동 검증 보강 |

### Result

초기 4층 규모의 프로토타입에서 출발해 8층 규모의 게임으로 확장했습니다.

- 보스 및 전투 패턴
- 화염·서리·독·번개 성장 시스템
- 보조 스킬과 궁극기
- 유물·보상·이벤트
- 저장 / 재개 및 이전 버전 저장 호환
- 모바일 터치 조작 및 반응형 화면
- 별도 보스 테스트 모드
- 전투 시뮬레이션과 QA 화면

기능이 늘어나면서 변경으로 기존 동작이 깨지는 문제를 줄이기 위해 자동 검증도 함께 확장했습니다. 구축 초기 **42개 수준이던 자동 검사는 최신 커밋 기준 327개까지 증가**했고, 보스·전투 구간에 대한 CPU 시뮬레이션과 별도 QA 화면도 추가했습니다.

자동 테스트가 통과하더라도 실제 조작감이나 체감 난이도까지 검증됐다고 보지 않고, 자동 검증과 사람의 플레이 테스트를 구분해 개발했습니다.

# 2. Workdog

## 실제 문서 관리 문제를 해결하기 위해 만든 AI 문서 아카이브

🔗 [Backend / Archive](https://github.com/baggam-dev/workdog-archive)  
🔗 [React Frontend](https://github.com/baggam-dev/workdog-archive-web)  
🔗 [Portal](https://github.com/baggam-dev/workdog-portal)

### Problem

업무나 개인적으로 문서를 저장해도 시간이 지나면 파일명만으로는 필요한 내용을 다시 찾기 어렵습니다. 특히 HWP, PDF, Excel 등 형식이 섞여 있으면 문서 내용을 기준으로 분류하고 검색하기가 더 어렵습니다.

### Approach

문서를 업로드하면 텍스트를 추출하고 AI가 내용을 요약·분류한 뒤, 검색과 관리가 가능한 웹 애플리케이션으로 만드는 구조를 설계했습니다.

전체 구조와 요구사항은 제가 정하고, Codex에 기능 단위 구현을 맡기는 방식으로 개발했습니다.

### Implemented

- HWP / PDF / XLSX / XLS / TXT 업로드
- 문서 텍스트 추출
- AI 기반 한줄 요약 / 핵심 포인트 / 카테고리 / 태그 생성
- 제목·태그·카테고리·파일 형식 검색 및 필터
- 폴더 / 메모 / 중요 문서 관리
- React 기반 프론트엔드 분리
- 모바일 카드 / 데스크톱 테이블 UI
- 네트워크·5xx 오류 재시도 및 사용자 오류 표시

HWP 문서의 표와 중첩 구조처럼 단순 텍스트 추출로 처리하기 어려운 부분은 여러 파싱 방식을 비교하고 구현을 반복하면서 구조화된 블록으로 변환하는 방식을 보완했습니다.

### Result

단순 CRUD 예제가 아니라, **문서 입력 → 내용 추출 → AI 처리 → 검색/관리**까지 하나의 흐름으로 동작하는 웹앱을 구현했습니다.

초기 Node.js/Express 기반 화면에서 시작해 기존 API를 유지하면서 React 프론트엔드를 별도 애플리케이션으로 분리했고, 실제 운영을 고려한 문서 관리와 오류 처리 기능을 단계적으로 추가했습니다.

# 3. Work Case

## 복잡한 계산 로직의 Rule Engine 전환 검토

> 회사 코드와 데이터는 공개하지 않고, 문제 해결 과정만 정리했습니다.

### Problem

복잡한 계산 규칙이 코드에 직접 구현되어 있을 때 규칙이 늘어나거나 변경될수록 유지보수 부담과 변경 영향도가 커지는 문제가 있습니다.

### AI Usage

ChatGPT와 Claude를 이용해 다음 대안을 빠르게 비교하고 프로토타입을 만들었습니다.

- JSON 기반 Rule Engine
- 규칙과 실행 로직의 분리
- 자연어에 가까운 규칙 표현
- 기존 방식과의 구현 복잡도 비교

### Verification

“구현할 수 있는가”에서 끝내지 않고, 실제 업무에서 예상되는 **수만 건 단위 처리**를 기준으로 성능을 측정했습니다.

### Result

규칙을 외부화하는 구조적 유연성은 확인했지만, 현재 업무 조건에서는 기존 구현 방식보다 명확한 성능상의 이점을 얻기 어렵다고 판단해 실제 시스템에는 적용하지 않았습니다.

결과적으로 AI를 이용해 여러 접근을 빠르게 프로토타입으로 만들고, **적용 가치가 낮은 방법을 개발 초기에 제외**할 수 있었습니다.

이 경험 이후 AI를 사용할 때도 “만들 수 있는가”와 “실제 시스템에 쓸 가치가 있는가”를 별개의 질문으로 보고 있습니다.

## Principle

**AI Output ≠ Final Answer**

AI는 짧은 시간 안에 여러 가능성을 실제 결과물로 바꾸는 데 강점이 있습니다.

다만 실제 적용 여부는 성능, 정확성, 안정성, 유지보수성과 같은 기존 엔지니어링 기준으로 직접 판단합니다.
